# Decision D14: Accept Cache-Miss CPU Above 10 ms for Now, and Watch It

- **Date**: 2026-11-26
- **Spec**: [SPEC-002a](../specs/SPEC-002a-master-data-schema-seed-public-read.md)
- **Related**: [D13](D13.md) (Workers Cache), `TODO-018` (pre-rendered body), `TODO-020` (cache and CPU observability)
- **Status**: APPROVED (owner, 2026-11-26)

## 1. Context & Problem Statement
SPEC-002a was measured on staging on 2026-11-26 with 140 cache-busting requests read through `wrangler tail`. The 10 ms CPU target of the Workers Free plan is missed on cache misses:

| Endpoint | p50 | p90 | p99 |
| :--- | :--- | :--- | :--- |
| `/v1/cards` | 9 ms | 33 ms | 45 ms |
| `/v1/daily-cards` | 10 ms | 20 ms | 41 ms |
| `/v1/card-art` | 4 ms | 7 ms | 12 ms |
| `/v1/reading-config` | 5 ms | 7 ms | 17 ms |

All 140 requests returned `ok`, with no exception and no error 1102. Cache hits run no Worker code (D13), so misses are only the first request per cache key and data center every 10 minutes, plus the first after each deploy.

## 2. Decision
Keep the current implementation on the Free plan. Do not start `TODO-018` and do not upgrade to Workers Paid yet. Watch for errors and CPU on misses, as `TODO-020` describes.

## 3. Rationale
- **Security (#1)**: No change to the attack surface. A miss that is cut off returns an error, and errors are `no-store`, so the next request retries.
- **Technical Debt (#2)**: `TODO-018` would duplicate the assembly rules and force SPEC-002b to regenerate stored bodies on every write. That cost is not justified while no request has failed.
- **Speed (#3)**: Nothing to build now.

## 4. Consequences
- Revisit this before the production frontend reads the API, or as soon as any error 1102 or failed master-data request shows up in logs. The two options stay open: `TODO-018` (spec change) or Workers Paid (owner approval for the cost).
- The staging frontend reads master data from the API with the bundled JSON as fallback, so a failed miss degrades to the bundled data instead of a broken page.
