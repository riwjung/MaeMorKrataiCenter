# Decision D13: Enable Workers Cache on `client` for Master-Data GETs

- **Date**: 2026-11-25
- **Spec**: [SPEC-002a](../specs/SPEC-002a-master-data-schema-seed-public-read.md)
- **Related**: [D05](D05.md) (10-minute TTL, no invalidation), D04 (`docs/client/decisions/D04.md`, public client security baseline), [research 2026-11-20](../researches/2026-11-20-workers-cache-invalidation.md) §3.3
- **Status**: APPROVED (owner, 2026-11-25)

## 1. Context & Problem Statement
The SPEC-002a estimate found two Free-plan risks:
- **D1 rows read.** Every new visitor reaches D1: about 1,560 rows for cards plus daily cards. The 5M rows/day limit is reached at about 3,200 visitors a day, after which every endpoint returns `503` until 00:00 UTC.
- **CPU.** Assembling 255–359 KB responses may exceed the 10 ms CPU limit.

D05 assumed edge caching would only start once a custom domain exists, because `caches.default` is a no-op on `*.workers.dev`. The 2026-11-20 research also found **Workers Cache**: a tiered, read-through cache in front of the Worker that works on `workers.dev` on every plan. It is enabled in Wrangler config (`[cache] enabled = true`, Wrangler ≥ 4.69; the repo uses 4.168) and follows the response's `Cache-Control`. A hit does not run the Worker, so it uses no CPU and reads no D1 rows.

## 2. Decision
1. Enable Workers Cache for the `client` Worker in every environment through `client/wrangler.toml`. No Rust code is needed to enable it. The planner confirms the exact config key against the current Cloudflare docs.
2. **No purge.** D05 stays as it is: admin edits may take up to 10 minutes to show, and invalidation remains `TODO-011`. Workers Cache purge (Option B in the research) is not used.
3. **Only 200 master-data responses are cacheable.** They already carry `Cache-Control: public, max-age=600`. Every other response (`/health`, 4xx, 429, 5xx) is `no-store`, so it is never cached.
4. `Vary: Origin` stays, so each allowed origin gets its own cache entry and its own `Access-Control-Allow-Origin`. The cache key includes the Worker version (the default), so a deploy starts with an empty cache.

## 3. Rationale
- **Security (#1).** Only public, non-personal data is cached. No secrets, tokens or new bindings are added. The D04 rate limiter exists to protect D1 and CPU, and a hit uses neither. Hits still count toward the 100k requests/day limit, but rate-limited requests counted toward it too.
- **Technical Debt (#2).** It is one config block, with no cache code or memo state in the Worker. A later custom domain or purge (TODO-011) builds on the same headers.
- **Speed (#3).** It is far smaller than an in-isolate memo, and it removes the D1 risk and most of the CPU risk for repeated requests.

## 4. Consequences and Accepted Trade-offs
- **On a hit, the Worker does not run.** The rate limiter, request-id middleware and logging are skipped, and the cached response carries the `x-request-id` of the request that filled the cache. D04 is amended accordingly: rate limiting and request ids apply to requests that reach the Worker.
- **Misses must still fit the CPU limit.** The first request per cache key and data center, and the first after each deploy, runs the Worker. Assembly under 10 ms (estimate risk 1, battleground B1) is still required, and CPU on a miss is measured on staging.
- **Local tests cannot exercise the cache** (Cloudflare: test on a deployed Worker). Verification on staging covers these checks:
  - A second identical request is a hit, and the cached response includes the 359 KB `daily-cards` body.
  - The response carries an `Age` header, so a browser's remaining freshness is `600 − Age` and total staleness stays within D05's 10 minutes. If staging shows no `Age` header, the worst case is about 20 minutes (edge plus browser), and the owner decides whether to accept that or split the TTL. Splitting it would be a contract change.
  - Errors and `/health` are not cached.
- The estimate's per-isolate memo option (B2) is dropped.
