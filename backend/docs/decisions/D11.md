# Decision D11: Split SPEC-002 into Read (SPEC-002a) and Write (SPEC-002b)

- **Date**: 2026-11-25
- **Spec**: [SPEC-002](../specs/SPEC-002-master-data-to-backend.md) → [SPEC-002a](../specs/SPEC-002a-master-data-schema-seed-public-read.md), [SPEC-002b](../specs/SPEC-002b-master-data-admin-write.md)
- **Status**: APPROVED (owner, 2026-11-25)

## 1. Context & Problem Statement
SPEC-002 was approved as one spec with 29 acceptance scenarios: public read endpoints on `client` plus 36 admin operations on `admin`. Since 2026-11-24 one person maintains the project. The customer-facing value (the site reading master data from the API) needs only the read half, while the write half is the larger and riskier part. Shipping both as one plan delays the first deployable result.

## 2. Decision
1. **Boundary: read / write.**
   - **SPEC-002a** delivers the complete D1 schema for every SPEC-002 master-data table, the seed (D07), the four public `client` GETs, `405` for writes on `client` master-data paths, and conformance to `docs/api/client/openapi.yaml`.
   - **SPEC-002b** delivers every `admin` master-data endpoint (uncached reads and create/update/delete), payload validation (SPEC-002 §4.5), reference and key errors as `400`/`404`/`409`, audit rows, the daily `updated`/`version` bump, category delete to uncategorized (D10), and conformance to `docs/api/admin/openapi.yaml`.
   - Read-side logic that only writes can trigger in production (uncategorized lists, love situations listed as uncategorized while no `love` category exists) is implemented and tested in SPEC-002a with direct database fixtures; SPEC-002b re-tests it end to end through admin writes.
2. **Order**: SPEC-002a is planned, executed, verified and deployed to staging first. SPEC-002b starts after SPEC-002a is verified and relies on its schema.
3. **Frontend switch stays outside both specs.** Changing `frontend-client` to fetch from the API (with the bundled JSON as fallback) is frontend work done after SPEC-002a reaches staging. `GEMINI.md` keeps backend agents out of frontend folders.
4. **Complexity**: both sub-specs are `complex` (planners on Opus, medium effort). The owner chose `complex` for SPEC-002a because the ten tables it designs are the base SPEC-002b builds on.
5. **Contract review**: the frontend-review step that SPEC-002 asked for in a PR is done by the owner while planning each sub-spec; there is no second approver.
6. **Uncategorized order** (gap found in the split audit): when `uncategorized_situations` holds both regular situations whose category was deleted and love-derived situations (no `love` category), the regular ones come first (by `sort_order`, then key), followed by the love-derived ones (by `reading_sort_order`). The client contract description was updated to match.

## 3. Rationale
- **Security (#1)**: The first deploy exposes only read-only, cached, rate-limited GETs; the write surface ships later behind the existing admin auth.
- **Technical Debt (#2)**: The full schema lands once in SPEC-002a, so SPEC-002b adds no migration for SPEC-002 data unless its audit finds a gap (logged as a new decision).
- **Speed (#3)**: The site can read master data from D1 after one plan instead of two.

## 4. Consequences
- SPEC-002 stays `APPROVED` as the parent and remains the normative definition of the data (§4). Plans are made from the sub-specs only.
- Every SPEC-002 requirement and scenario is assigned to exactly one sub-spec; see the traceability table below.
