## 1. Objective & Architecture Impact
`client` gains four public, read-only, cached GETs (`/v1/cards`, `/v1/daily-cards`, `/v1/card-art`, `/v1/reading-config`) served from the shared D1 tables that p1 creates and seeds, a `405`/`404` fallback for every route (D12), and Workers Cache (D13).

New and changed pieces, all inside `client` plus two Makefile targets and one script:
- `client/src/master_data.rs`: typed rows (port output), typed response structs, and the pure assembly (sorting, null fill of love-status maps, `missing_fields`, uncategorized lists, `situations.love`). It is the only place these rules live.
- `client/src/adapters/d1_master_data.rs`: static `SELECT` constants (one `row_json` TEXT column per row, built with `json_object`), the batched D1 call, and pure `*_from_sets` parse functions.
- `MasterDataPort` (read methods only) on `ClientPorts`, implemented by `WorkerClientAdapter` (D1 binding `DB`) and `MemoryClientStore` (fixture rows, D1-failure switch `d1_healthy`, read counter).
- `client/src/routes/master_data.rs`: four handlers; `200` gets `Cache-Control: public, max-age=600` and `Vary: Origin`. The existing middleware keeps a handler's `Cache-Control` and forces `no-store` on everything else, so it does not change.
- `Router::method_not_allowed_fallback` → `405` + `Allow: GET,HEAD` + envelope `METHOD_NOT_ALLOWED` + `no-store` on all known paths including `/health`. Unknown paths keep the `404` fallback.
- `client/wrangler.toml`: `[cache] enabled = true` at top level, staging and prod.
- Tests: host tests with the memory adapter (tiny fixture and full seed golden values), the real-SQLite D1 test (`make test-d1-read`, part of `make test-d1`), and `make smoke-local` (local Worker + local D1 + curl).

One new dev-dependency on the dev-only workspace crate `tools/d1-local` (p1 task 02; used only by `client/tests/d1_master_data_sql.rs`, never built for wasm32). No change to `admin`, migrations, seed or the contract. `client` never writes master data: the port has no write method, and a unit test asserts that every SQL constant is a single `SELECT`.

**Execution order and preconditions.** Tasks run strictly in order, one fresh Executor per task.
- Tasks 01 to 05 need only this repo (memory adapter, hand-built fixtures). They can start before p1 is merged, once the Plan Auditor freezes the contract.
- Tasks 06 to 08 need p1 merged (`seed/*.json`, `migrations/0002_master_data.sql`, `make seed-build`, `make seed-local`, `make test-d1`, the `tools/d1-local` crate).
- The owner's Mac has 8 GB RAM. Every cargo command uses the lean env given in each task, and only one Executor runs cargo at a time.

## 2. Battleground Summary
- **B1, response assembly under 10 ms CPU** ([debate](../../battlegrounds/SPEC-002a-p2-public-read/01-master-data-assembly/debate.md), contenders on sonnet/medium). Winner: Option B. SQL returns one `json_object` string per row, with love-status texts folded in by `json_group_object`. Rust parses each into typed rows with serde_json and runs one shared pure assembly. This means about 78 boundary crossings per endpoint instead of about 1,000. The contract stays in typed Rust, and there is no duplicated logic. Option C (whole document in SQL) has the lowest CPU but puts the rules in SQL twice and ships unvalidated strings. It is the documented fallback if staging shows misses above about 8 ms (P2-PS1). CPU is measured on staging, not locally (§5).
- **Method fallback and cache headers** ([debate](../../battlegrounds/SPEC-002a-p2-public-read/04-method-fallback-and-cache-headers/debate.md)). Winner: router-level `method_not_allowed_fallback` (axum keeps `Allow`), with headers set in the handler on `200` only. `Vary: Origin` is always set on `200`, because Workers Cache honors `Vary` and a no-Origin variant must never be served to browsers.
- **Real-SQLite test of the adapter SQL** (p2's part of B3, [debate](../../battlegrounds/SPEC-002a-p2-public-read/07-d1-sql-tests/debate.md)). Winner: an `#[ignore]` Rust integration test in the `client` crate, reusing the production SQL constants, parse and assembly functions and the seed golden assertions. **Plan Auditor decision on the harness:** it drives local D1 through `d1_local::D1Local` (the dev-only crate that p1 task 02 creates; `target/tmp/d1/<name>` state), not through a private copy of the wrangler driver the debate had proposed (`target/test-d1-read`), and `tools/seed-build` stays free of any dependency on `client`.

## 5. Staging verification checklist (owner / Verifier, not an Executor step)
Staging deploy and seed load are owner-approved `[CLOUD]` steps. Order:
1. Local (no cloud change): `make cf-dry-run ENV=staging` passes, which proves wrangler accepts `[env.staging.cache]`.
2. `[CLOUD]`, owner approves each: `make migrate-staging`, `make seed-staging` (p1), `make deploy-staging`.

Read-only checks with `S=https://maemorkratai-backend-client-staging.maemorkratai.workers.dev` and `O=https://staging.maemorkratai.com`. The rate limit is 60 requests per minute per path and IP, so wait a minute between the CPU batches.

1. **Hit including the 359 KB body.** Run `curl -s -D h1 -o b1 $S/v1/daily-cards; curl -s -D h2 -o b2 $S/v1/daily-cards`. Expected:
   - both `200` with `cache-control: public, max-age=600` and `vary: Origin`
   - `h2` shows `cf-cache-status: HIT` (header name per the Workers Cache debugging docs)
   - `cmp b1 b2` reports no difference, and `wc -c b2` is about 359,000
   - repeat for `/v1/cards` (about 255 KB)
2. **`Age` header.** `h2` carries `age: <seconds>`. If it does not, the worst-case staleness is about 20 minutes (edge plus browser), and the owner decides per D13 whether to accept it (open question Q1).
3. **Variants per Origin.** Send `curl -s -D - -o /dev/null -H "Origin: $O" $S/v1/cards` twice. The second is a `HIT`, and both carry `access-control-allow-origin: $O`. A following request without `Origin` must not carry `access-control-allow-origin`.
4. **Errors and `/health` are not cached.** Send each of these twice:
   - `curl -s -D - -o /dev/null -X POST $S/v1/cards`: `405`, `allow: GET,HEAD`, `cache-control: no-store`
   - `curl -s -D - -o /dev/null $S/v1/nope`: `404`, `no-store`
   - `curl -s -D - -o /dev/null $S/health`: `503` because staging has no R2, `no-store`

   No response shows `cf-cache-status: HIT`.
5. **CPU on a miss.** In one terminal run `cd client && npx wrangler tail --env staging --format json`. In another run `for i in $(seq 1 50); do curl -s -o /dev/null "$S/v1/daily-cards?cb=$(date +%s)$i"; done`, wait 60 s, then do the same for `/v1/cards`. A unique query string changes the cache key, so every request is a miss. Read `cpuTime` from the tail events, or use the CPU time percentiles in the dashboard. Pass: p99 under 10 ms and no request failed with error 1102. If p99 is above about 8 ms, the owner decides between P2-PS1 and the Paid plan.
6. Optional: D1 dashboard rows read for the period match about 1,014 per `/v1/cards` miss and about 546 per `/v1/daily-cards` miss, and are near zero for hits.
